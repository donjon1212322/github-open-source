## Зачем

GitHub `schedule` не гарантирует доставку. 06.11 не пришли запуски в 07:27,
09:27, 11:27, 13:27 по Минску, а после 10:27 не было ни одного запуска 3 ч
26 мин; штатный `collect` за 06.11 вообще пришёл лишь в **15:20** вместо 07:23.
Внешний будильник дёргает **API** (`repository_dispatch`), а не общую очередь
расписаний GitHub, поэтому создание запуска от GitHub-планировщика не зависит.

## Что сделано в репозитории

- `watchdog.yml` принимает `repository_dispatch` с `types: [watchdog_tick]`;
- вторая cron-строка `57 */2 * * *` как резервный тик;
- `queue: max` в общей группе `state-writer` не даёт отменить созданный запуск;
- watchdog подтверждает слот по state, повторяет не чаще 30 минут и больше не
  шлёт тревожное сообщение на первый успешный dispatch.

## Как развёрнуто (для восстановления)

```bash
cd tools/external_tick
cp wrangler.toml.example wrangler.toml   # вписать name, account_id, GH_REPO
npx wrangler deploy                      # cron из [triggers]
printf '%s' "$GH_PAT" | npx wrangler secret put GH_PAT
npx wrangler secret list                 # только имена, без значений
```

Официальные лимиты Workers Free: **5 Cron Triggers на аккаунт**,
**100 000 запросов/сутки**, 10 мс CPU. Живой `*/30` = 48 вызовов/сутки.
Подготовленный `* * * * *` = 1440 вызовов/сутки (~1,44 % лимита),по-прежнему **один** cron trigger; только нужные минуты дёргают GitHub.
Секрет в репозиторий не попадает; `wrangler secret put` кладёт его в Cloudflare.

## Важные уроки эксплуатации

- **После `wrangler deploy` расписание подхватывается не сразу** (несколько
  минут). При отладке 06.11 четыре передеплоя подряд всё время сбрасывали
  таймер — первые тики пришли только когда деплои прекратились. Не дёргайте
  прод без нужды.
- Cron в Cloudflare считается по UTC; `*/30` = :00 и :30 каждого часа UTC,
  то есть :00 и :30 по Минску тоже (UTC+3).
- Если **отозвать `GH_PAT`**, будильник встанет. Сначала замените секрет, потом
  отзывайте старый токен.
- `repository_dispatch` создаёт run сразу, но job может встать в очередь при
  нагрузке GitHub; `queue: max` защищает от отмены, не от задержки.
- Штатные cron-строки в `watchdog.yml` удалять нельзя — они второй канал.

## Ротация токенов (обязательно, по порядку)

1. **Cloudflare API Token**, которым выполнялся деплой, отозвать сразу:
   My Profile → API Tokens → Revoke. После деплоя он не нужен.
2. Сейчас в секрете `GH_PAT` лежит старый PAT из переписки. Создайте **новый
   fine-grained PAT** (`Actions: write`, только `github-open-source`) и замените
   секрет: панель Cloudflare → `ghos-v6-tick` → Settings → Variables and
   Secrets → `GH_PAT`, либо `printf '%s' "$NEW_PAT" | npx wrangler secret put GH_PAT`.
3. Только после замены отзовите оба старых PAT из переписки.

Ограничения: таймаут 30 с, нет авто-ретраев, отключение после 25 подряд неудач.

**Свой ПК / Raspberry Pi:** обычный `cron` с тем же `curl` каждые 30 минут —
нужен постоянно включённый компьютер.

## Честно про гарантии

**100% гарантии нет.** У Cloudflare Cron Triggers тоже нет автоматических
повторов и алертов об ошибке; `503` у Gemini, недоступность Telegram/dev.to и
очереди GitHub никуда не делись. Система стала заметно надёжнее: пропущенный
тик подхватывается следующим через 30 минут, штатные cron GitHub остаются вторым
каналом, а watchdog догоняет пропущенные слоты по state и сообщает владельцу
только при реальной проблеме.

**Не менять:** `timezone`, UTC-сутки, лимит 3 поста/день и Make.com — это
отдельные решения владельца.


## 07.11.2026: поминутный тик (задеплоен 13:47 Минск)

В `worker.js` добавлена таблица `SLOTS`: на каждую UTC-минуту сверяется
`event.scheduledTime`, и если слот due — уходит `POST /actions/workflows/
pipeline.yml/dispatches` с `inputs` прямо в `main`. `watchdog_tick` остаётся
на :00 и :30. GitHub `schedule` не удаляется (fallback), Watchdog — вторая
линия. Идемпотентность слотов в state не даёт задвоить публикацию, если
придут и внешний dispatch, и запоздавший GitHub cron.

**Лимиты и деньги.** Workers Free: 100 000 запросов/сутки на аккаунт, 10 мс
CPU на вызов, 5 cron trigger'ов на аккаунт, минимальная гранулярность
1 минута. 1440 вызовов/сутки — ~1,44 % дневной квоты; CPU уходит на один
`fetch` (ожидание сети не считается) и сравнение строк. GitHub получает
~23 ежедневных `workflow_dispatch` + 3 еженедельных (воскресенье/четверг)
+ 48 `repository_dispatch` в сутки вместо 48.
Новых платных сервисов нет, доплаты нет. Квота общая на аккаунт: если другие
Worker'ы (`ogonek-test`, `gpbot`) внезапно начнут есть её, наш вклад всё
равно мал, но гарантии нет.

**100 % не будет.** Cloudflare запускает cron «около» нужной минуты (джиттер
в секундах), не ретраит упавший вызов и не шлёт алерт; GitHub Actions может
поставить job в очередь; Gemini может отдать `503`, а Telegram/dev.to/`t.me`
быть недоступны; токены истекают. Реалистичный результат — «обычно в ту же
минуту, а не через 4–7 часов», с Watchdog как страховкой. Точных минут и
100 % не обещаем.

**Деплой и что осталось владельцу.** Сделан один `wrangler deploy` (повторные
передеплои 06.11 сбивали таймер, поэтому больше не дёргаем): schedule
`* * * * *`, HTTP 200, секрет `GH_PAT` и var `GH_REPO` на месте. Первый
`workflow_dispatch` по due-слоту ожидается в **15:43 Минск** (midday); до
него в проде подтвержден только канал `watchdog_tick`.

Cloudflare API Token, присланный в чате 07.11 и использованный для деплоя,
тоже скомпрометирован: он не записан в файлы и после деплоя больше не нужен —
**отзовите его**. Затем замените секрет `GH_PAT` новым fine-grained PAT с
`Contents: write` (для `repository_dispatch`/`watchdog_tick`) **и**
`Actions: write` (для нового `workflow_dispatch`) и только после этого
отзывайте оба старых GitHub PAT. Значение текущего секрета прочитать нельзя
(Cloudflare secrets write-only), поэтому наличие у него `Actions: write`
не проверено: если due-слоты вернут `403` в логах Worker, ротация нужна
срочно, а до неё сработает штатный GitHub cron как fallback.


## Недельные слоты и идемпотентность (08.11)

Раньше `digest`, `report` и `poll-close` были единственными слотами без
страховки: повторный запуск создал бы второй дайджест / опрос / отчёт.
Теперь каждая из этих команд пишет маркер ISO-недели в `last_runs`
(`week`, `finished_at`) **после** успешного побочного эффекта; повтор в ту же
неделю честно возвращает `<name>_already_done` и ничего не шлёт.
`close_poll_command()` помечает неделю и при `no_active_poll`, чтобы Watchdog
не дёргал слот каждые 30 минут.

Поэтому в `worker.js` добавлены due-слоты с третьим параметром — UTC-днём
недели (`getUTCDay()`: 0 = воскресенье, 4 = четверг):

```
["16:13", { command: "digest" }, 0]      // 19:13 Минск, воскресенье
["16:43", { command: "report" }, 0]      // 19:43 Минск, воскресенье
["18:53", { command: "poll-close" }, 4]  // 21:53 Минск, четверг
```

`facebook-handoff` по-прежнему **не**dispatch-ится внешним будильником
(owner rule «мейк не трогай»): у него нет идемпотентного guard, и повтор
удвоил бы строку в Sheet.

`watchdog.WEEKLY_SLOTS` — вторая линия: на нужном дне недели, после дедлайна
(16:20Z digest, 16:50Z report, 19:00Z poll-close), если маркера недели нет.
Родной GitHub cron, due-диспатч Worker и восстановление Watchdog могут все
сработать в одну неделю — дубля не будет, вторые вызовы станут no-op.
Точную минуту гарантирует только due-слот Worker; Watchdog догоняет не позже
ближайшего :00/:30. **100 % по-прежнему нет**: Cloudflare Cron Triggers без
ретраев, дальше очередь GitHub Actions, Gemini, Telegram и dev.to.


## 11.11: почему посты всё равно опаздывали (и что исправлено)

Due-слоты Worker работали идеально: все publishing-команды создавались в
нужную минуту и стартовали с нулевой задержкой. Опоздание в часах давали
**вторые**, запоздалые `schedule`-события GitHub: тот же слот приходил через
7 часов, публиковал дубликат уже в следующих UTC-сутках и занимал квоту
следующего дня. С 11.11 `cli._run_scheduled()` такие события игнорирует
(допуск 15 минут), а Watchdog остаётся страховкой на случай, если due-слот
действительно не отработал. `worker.js` в этот раз **не деплоился** —
исправление на стороне репозитория; деплой потребовал бы Cloudflare API
токена, которого в сессии нет. Перед любым будущим деплоем сначала
замените `GH_PAT`, иначе тик остановится.
