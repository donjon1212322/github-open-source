# Эксплуатация

Что делать каждый день, что делать, когда сломалось, и как откатить.

> **State.** Живой `state/state.json` и `state/events.jsonl` лежат в
> orphan-ветке `state`, а не в `main`. Перед любой локальной командой ниже
> загрузите их: `python tools/state_branch.py read` (нужен `GH_TOKEN`).
> Файлы `state/` в `main` — пустой bootstrap; править их бессмысленно,
> изменения всё равно придут CAS-записью из workflow.

### Частые поломки

**Пост не вышел.**
```bash
python tools/state_branch.py read
tail -20 state/events.jsonl | grep publish
```
`no_candidate` → очередь пуста, `collect` не отработал.
`daily_limit_reached` → норма, лимит 3.
`all_candidates_rejected` → гоут отсёк всех, смотреть `rejections`.

**Превью не отображается.**
Проверить `IMGBB_API_KEY`. Если пуст — карточка не загрузится, пост уйдёт
без превью с записью в лог. Telegraph — резерв, но он хуже.

**AI Brief молчит.**
```bash
PYTHONPATH=src python3 -m ghos_v6.cli news --force
```
В ответе `rejections` — по каждой причине. Если `sponsored` — проверить,
не изменился ли формат спонсорской строки у канала.

**Кросс-посты не уходят.**
Проверить `FEATURE_BLUESKY`. Для Facebook —
`FEATURE_SHEETS_HANDOFF` и наличие `GOOGLE_SERVICE_ACCOUNT_JSON`; Page-токен
не нужен и в v6 не читается.
Потом `crossposts.*.status` в записи поста: `pending` → `sent` или
`dead_letter`.

**Дубликат в канале.**
`dedup.check` пропустил. Смотреть `seen_repos` по этому проекту.
Причина обычно — изменился README и отпечаток не совпал.

## Инциденты

### Опубликован плохой пост

Telegram-канал: удалить сообщение руками. Бот не умеет отзывать.
Затем запустить `Publishing pipeline → moderation` (или `report`) — состояние
запишется в ветку `state` штатным CAS-коммитом. **Не правьте bootstrap в
`main`**: workflow его всё равно перезапишет при чтении, а CI запретит
появление там реальных записей.

### Утёк секрет

1. Отозвать токен у провайдера **сразу**.
2. Заменить в Settings → Secrets.
3. `python3 tools/secret_scan.py` — проверить репозиторий.
4. Секреты никогда не печатать в чат.

### Публикация ушла не в тот канал

`Config.telegram_chat_id` не откатывается молча на основной. Если это
случилось — значит `TELEGRAM_TEST_CHANNEL_ID` был пуст, и код должен был
упасть, но не упал. Проверить `config.py`.

### GitHub Actions не запускаются

Проверить, не `disabled_manually`:
```bash
gh api repos/{owner}/{repo}/actions/workflows
```
**С 03.11.2026 владелец разрешил включать `Doctor` и `Publishing pipeline`.**
До переключения на `main` держим `APP_ENV=test` / `PUBLISH_TARGET=test`;
если workflow снова окажутся выключены после 60 дней без коммитов — включить
повторно (`Lifecycle guard` создаёт issue по этому поводу).

**Не запускайте ручные dispatch пачкой.** У `pipeline.yml` общая группа
`concurrency: state-writer` с `cancel-in-progress: false`: GitHub держит не
более одного выполняющегося и одного ожидающего запуска, поэтому из 10
одновременно отправленных команд 8 были `cancelled` (проверено 03.11.2026).
Отправляйте по одной и дожидайтесь завершения; штатные cron не конфликтуют,
потому что идут по расписанию.

## Откат

### Откатить пост-формат

Форматтер — `formatter.py::format_project_post`. Вернуть прошлую версию:
```bash
git log --oneline -- src/ghos_v6/formatter.py
git revert <commit>
```

### Откатить всю публикацию

```bash
APP_ENV=test
PUBLISH_TARGET=test
```
Публикация в основной канал прекратится немедленно, тестовый продолжит
работать. Это штатный способ.

### Откатить состояние

Живой state лежит в orphan-ветке `state`, история коммитов `chore(state):`.
```bash
git fetch origin state
git log --oneline FETCH_HEAD -- state/state.json | head
git show FETCH_HEAD:state/state.json | head
export GH_TOKEN=... GITHUB_REPOSITORY=donjon1212322/github-open-source
python tools/state_branch.py read --out /tmp/live-state   # текущее состояние
python tools/state_branch.py status                        # размер, свежесть, main
```
Восстановление файла делается через `tools/state_branch.py squash` после
ручной правки в `/tmp/live-state`; `main` при этом не трогается. Осторожно:
откат вернёт проекты в очередь, и они могут выйти повторно.

### Watchdog и восстановление слотов (исправлено 06.11)

`pipeline.yml` и `watchdog.yml` остаются в общей группе `state-writer`, чтобы
запись `state` была сериализованной, но получили `queue: max`: несколько
ожидающих запусков больше не вытесняют друг друга. Раньше созданный watchdog'ом
`workflow_dispatch` отменялся следующим scheduled run до старта job.

Watchdog следит за `collect`, тремя publish-слотами, AI Brief, **article of
the day** и **второй статьёй dev.to** (`news-article`, дедлайн 20:30 UTC). Маркер в `last_runs.watchdog_dispatches` считается подтверждённым
только когда факт появился в `state`: `last_runs.*.finished_at`,
`news_topics[].published_at` или `published[].articles.devto.published_at`.
Сам `HTTP 204` подтверждением **не** считается; неподтверждённый слот можно
повторить не чаще раза в 30 минут. Для article есть два дополнительных guards:
без проектного поста за этот UTC-день команда не запускается, и статья старше
6 часов после дедлайна не догоняется задним числом.

Сутки в коде намеренно считаются по UTC: GitHub cron работает в UTC, а
`timezone: "Europe/Minsk"` владелец запретил добавлять. Перевод лимита
«3 поста в день» на минские сутки — отдельное решение, не входившее в это
исправление.

### Вторая правка 06.11: уведомления и внешний будильник

06.11 GitHub не доставил несколько штатных тиков подряд (07:27, 09:27, 11:27,
13:27 по Минску), а после 10:27 не создал ни одного запуска 3 часа 26 минут.
Из-за этого утренний пост 10:13 не вышел до ручного вмешательства. Заодно два
тревожных сообщения «⚠️ Пропущен слот» ушли по слотам, которые благополучно
завершились через три минуты, — обратного уведомления не было.

Что изменено:

- **Алерты больше не кричат «волк».** Первый принятый dispatch (`HTTP 204`)
  уходит тихо: это ещё не проблема, а только попытка. Владелец получает `⚠️`
  только если dispatch **не удался** или если неподтверждённый слот пришлось
  повторить (попытка №2 и далее). Когда факт появляется в `state`, приходит
  закрывающее `✅ Слот восстановлен`.
- **Два независимых тика.** К `27 */2 * * *` добавлена `57 */2 * * *`: при
  массовой недоставке шанс, что хоть один тик дойдёт, выше. Это снижение
  вероятности, а не гарантия.
- **Вход через API.** `watchdog.yml` теперь принимает `repository_dispatch` с
  `types: [watchdog_tick]`. Внешний бесплатный будильник дёргает
  `POST /repos/<owner>/<repo>/dispatches`, и запуск создаётся сразу, минуя
  best-effort планировщик GitHub. Готовый комплект и пошаговая инструкция —
  `tools/external_tick/README.md`.

**Внешний будильник подключён 06.11 в 15:30 Минск.** Worker `ghos-v6-tick` на
бесплатном Cloudflare с cron `*/30` дёргает `repository_dispatch`; первый
автоматический тик создал run `42218175231` (success, без публикаций). Детали и
порядок ротации токенов — `tools/external_tick/README.md`. После `wrangler
deploy` расписание подхватывается с задержкой в несколько минут, поэтому не
передеплоивайте Worker подряд.

**Честная граница:** 100% гарантии по-прежнему нет. У Cloudflare cron нет
авто-повторов; `repository_dispatch` создаёт run сразу, но job всё равно может
встать в очередь при нагрузке; `queue: max` защищает от отмены, не от задержки.
Штатные cron-строки удалять нельзя — они остаются вторым каналом. Make.com,
`timezone`, UTC-сутки и лимит 3 поста/день не менялись.

**Осталось за владельцем:** отозвать одноразовый Cloudflare API Token (после
деплоя не нужен) и заменить секрет `GH_PAT` новым fine-grained PAT, после чего
отозвать оба старых PAT из переписки. Пока секрет не заменён, отзыв старого PAT
остановит будильник.

### Третья правка 06.11: article не останавливается на дубликате

Вечером 06.11 watchdog четырежды догонял `article` и слал `⚠️`: штатный cron
статьи (16:33) не доставили, а `article_of_day()` брал проект с лучшим score
(`rehan-remade/universal-modder`), находил про него статью на dev.to от
23.10.2026 и **возвращал честный, но пустой отказ**, не пробуя два других
проекта за этот день. Watchdog же принимал как доказательство только
`published[].articles.devto.published_at`, поэтому считал слот невыполненным.

Что изменено:

- **Дубликат → следующий по рейтингу.** При `duplicate_repo_on_devto` цикл
  делает `continue`, а не `return`. Если все кандидаты уже освещены, возвращается
  `duplicate_repo_on_devto` с числом дублей.
- **Дешёвая проверка первой.** Индекс статей dev.to (`/api/articles/me/all`)
  запрашивается **один раз за запуск** до любых дорогих вызовов; дубликат,
  подтверждённый сегодня, берётся из кэша `devto_duplicate.checked_at` вообще
  без запроса. ImgBB-обложка и `publish_article` вызываются только для
  реального кандидата.
- **Явный факт «слот отработан».** Любой корректный исход `article_of_day()`
  (опубликовано / все дубли / нет проектов / уже публиковалось) пишет
  `last_runs.article.finished_at` за UTC-день. Watchdog принимает и этот факт,
  поэтому честный отказ больше не вызывает повторов и тревог.

`article_markdown` генерируется Gemini **раньше**, при публикации проекта в
канал, и нужен для карточки и Telegraph — article-команда не тратит токены
повторно. Экономятся запросы dev.to, ImgBB и пустые article-запуски.
Регрессии: `tests/test_article_fallback_2026_11_06.py`.

### Четвёртая правка 06.11: идемпотентность слотов и лимит

Вечерняя проверка расписания (до 12.11) показала две несогласованности.
Штатный cron `13 7 * * *` (утренний пост, 10:13 Минск) доставили только в
**18:04**, когда
watchdog уже догнал этот слот в 14:14, — и он опубликовал **второй** пост под
`europe_morning`, съев дневную квоту, предназначенную `us_peak`. А отказ
`daily_limit_reached` не писал `last_runs`, поэтому watchdog собирался всю ночь
догонять `publish:us_peak` и слать `⚠️` каждые 30 минут.

Что изменено в `publish_slot()`:

- **Слот идемпотентен.** Если `last_runs["publish:<slot>"].finished_at` уже
  относится к текущим UTC-суткам, команда возвращает `slot_already_done` без
  обращения к Gemini, Telegram и GitHub. Запоздавший cron больше не дублирует
  пост. `slot="manual"` исключён: это явная команда владельца, не ретрай
  планировщика.
- **Лимит = обработанный слот.** `daily_limit_reached` записывает
  `last_runs["publish:<slot>"]` с `reason` и `published: false`. Watchdog видит
  факт и не догоняет слот, по которому объективно нечего публиковать.

Сутки остались UTC (граница 03:00 Минск), `MAX_PROJECT_POSTS_PER_DAY = 3` не
менялся, `timezone` и Make не трогались. Регрессии:
`tests/test_publish_slot_idempotency_2026_11_06.py`.

**Честная граница:** это убирает задвоение и ложные тревоги, но **не делает
время публикации точным**. GitHub `schedule` по-прежнему best-effort; внешний
будильник будит watchdog, который догоняет слот **после дедлайна**. «Все слоты
за сутки отработаны» — да; «ровно в 10:13 / 15:43 / 20:18» — гарантии нет.

## Безопасность (после аудита 03.11.2026)

- `pipeline.yml` разделён на два job: `run` (read-only, секреты, без
  `persist-credentials`) и `commit-state` (write, без секретов и без запуска
  кода проекта). Не сливайте их обратно в один job.
- `requirements.lock` обязателен: `pip install --require-hashes -r
  requirements.lock`. Не заменяйте его на `pip install -e .` в CI.
- `main` защищён ruleset: force-push и удаление запрещены. Единственный
  force-update во всём проекте — ежемесячный `squash` ветки `state`.
- CodeQL и gitleaks включены. Dependabot version updates **отключены**
  (`.github/dependabot.yml` удалён 03.11.2026): его PR меняли закреплённые SHA
  экшенов и `requirements-dev.in` без пересборки хэш-локов, поэтому были
  несливаемым шумом. Dependabot **vulnerability alerts в Settings отключены**
  (не менялись), `automated-security-fixes=false` — значит Dependabot не
  создаёт здесь никаких PR и уведомлений. Secret scanning, push protection,
  CodeQL и gitleaks включены.
- При инциденте: `git revert` + новый релиз. Не правьте `state/state.json`
  руками при работающих кронах.

## Мониторинг и долгосрочная эксплуатация (с 03.11.2026)

| Сигнал | Где смотреть | Действие |
|---|---|---|
| `state.json` > 8 МиБ | `tools/state_branch.py status` в `Lifecycle guard` и `Doctor` | проверить компактирование, при необходимости архивировать полные записи; жёсткий отказ записи на 90 МиБ |
| Ветка `state` не менялась > 2 дней | heartbeat в `status` | `Lifecycle guard` создаёт issue; иначе через 60 дней GitHub отключит все schedule |
| state снова в `main` | CI `check-bootstrap`, `Doctor` | сборка красная: вернуть bootstrap и проверить, что `commit-state` пишет в ветку |
| `GEMINI_MODEL` исчез из API | `doctor` → `Gemini_models`, `Lifecycle guard` | сменить Variable на актуальную модель; проект fail-closed и молча перестанет публиковать |
| Рост ошибок кросс-постов | Actions → Publishing pipeline | разобрать `dead_letters`; Bluesky включён |
| Приближение к квоте артефактов | Billing → Usage, Budgets and alerts | артефакт создаётся только при изменении state (не на каждом из 64 запусков); триггер — размер, не число запусков |

Полный разбор: `docs/RUNBOOK.md` и отчёт о долгосрочных рисках.

### Письма об «ошибках» от Dependabot (03.11.2026)

Два письма вида `Re: [...] Bump github/codeql-action/analyze ... (PR #2)`
были **не поломкой продовой ветки**: Dependabot обновил `init` и `analyze`
двумя разными PR (#4 и #2), поэтому в `codeql.yml` на ветке PR оказались
версии 4.39.1 и 4.39.3 одновременно. CodeQL требует одинаковую версию у
всех своих шагов и падает с `configuration error`. Всего в истории репозитория
было ровно 2 failed-запуска, оба на ветках `dependabot/*`; на `main` оба шага
закреплены на одном SHA `793b778da9c9275a0f276522b27cb5fc14bba279`.

PR закрыты, ветки удалены, конфиг Dependabot удалён — новые такие письма не
придут. `tests/test_codeql_pins.py` и отдельная мутация запрещают рассинхрон:
если кто-то обновит только один из шагов, CI упадёт сразу, а не письмом на
почту. Проверить вручную: `Actions → CodeQL → Run workflow`.

## 13.11.2026 — семь писем об ошибках: диагноз и фикс

**Что пришло владельцу.** За 12.11 (18:53–23:54Z) упало **7 запусков**
`Publishing pipeline` — GitHub разослал письма о каждом. Разбор логов показал
не семь поломок, а **две причины и один шумный спутник**:

| Запуски | Команда | Причина |
|---|---|---|
| `43284509978`, `43285746630`, `43295997395`, `43301049661`, `43332716070` | `poll-close` | `stopPoll` → `Bad Request: poll can't be stopped` |
| `43288812931`, `43295992577` | `news` | `Gemini generateContent failed: ... high demand` (503) |
| в части тех же логов | `commit-state` | `##[error] Unable to download artifact(s): Artifact not found for name: state` |

**Корень №1 — опрос закрылся сам.** Опрос `3574` открыт 08.11 в 18:09Z с
`open_period = 96 ч`, значит Telegram автоматически закрыл его 12.11 в
18:09Z — за 44 минуты до штатного четвергового `18:53Z`. На `t.me/s` уже
видно «Final Results». `close_poll_command()` считал любой отказ `stopPoll`
жёсткой ошибкой (`ok: false`), не писал недельный маркер, поэтому сторож по
расписанию повторял попытку, а запоздалый родной cron `53 18 * * 4`
(исключение из late-guard) добавил пятую. Пять писем из семи — один и тот же
уже закрытый опрос. `learn` при этом отработал нормально.

**Корень №2 — временная перегрузка Gemini.** Две попытки AI Brief в 19:18Z и
20:00Z получили 503 «high demand». Исключение ушло в `cli.main`, который
послал владельцу alert и вернул exit 1, хотя сторож в 20:30Z успешно
догнал бриф (`3591`, 20:32Z), а вторую статью `5025588` — в 21:01Z.
То есть публикации не пострадали, а письма пришли.

**Спутник — ложная «ошибка» артефакта.** `commit-state` запускался через
`if: always()` даже когда state не менялся и артефакт не загружался;
`download-artifact` печатал `##[error]` (job при этом был `success`). Такая
строка есть и в успешных запусках без изменений state.

**Что исправлено:**

- `polls.DEFAULT_WEEK_POLL_HOURS = 120` (было 96): воскресный опрос теперь
  живёт до пятницы, и четверговый `stopPoll` всегда успевает до авто-закрытия.
  `docs/VALUE_SYSTEM.md`, `docs/agents/PRODUCT_REVIEW.md`, `OPERATIONS` обновлены.
- `close_poll_command()` различает «опрос уже закрыт» и настоящую ошибку.
  Уже закрытый → честный `ok: true, reason: poll_already_closed`, недельный
  маркер, `active_poll` очищен, **выдуманных голосов нет**; сетевой сбой
  по-прежнему `ok: false` и виден владельцу.
- `_transient_gemini_skip()` в `pipeline.py`: только временные 429/503
  превращаются в тихий `ok: true` **без маркера**, чтобы сторож повторил слот.
  Настоящие баги по-прежнему пробрасываются в `cli.main` и alert'ят.
  Применено к генерации брифа, пересборке второй статьи и публикации dev.to.
- `pipeline.yml`: `commit-state` стартует всегда, но перед скачиванием
  проверяет через Artifacts API, был ли реально загружен артефакт `state`.
  Так исчезла ложная `##[error]` и при этом state не может потеряться, если
  задание `run` упало и не отдало свои outputs (усиление 14.11).
- Регрессии в `tests/test_error_cleanup_2026_11_13.py` и 4 новые мутации.

**Что НЕ менялось:** расписание постов/статей, каденция, число постов,

## 14.11.2026 — группа обсуждений и закрепы

**Что подключено.** Канал `@GitHub_Open_Source` связан с приватной
супергруппой **«GitHub Open Source — Chat»** (ссылка-приглашение
`https://t.me/+GEPDTvHlBEo3NTRi`, 20 участников). Идентификатор связи
`linked_chat_id = -1003849113813`, бот `@open_source_GP_bot`. Связь создана в
самом Telegram; Bot API умеет её только читать, но не создавать и не разрывать.
Публичные посты канала по-прежнему без `reply_markup`, поэтому нативная кнопка
комментариев сохраняется.

**Почему появляются закрепы.** Это не команда нашего бота: в коде нет ни
одного `pinChatMessage`. Telegram сам пересылает КАЖДЫЙ пост канала в
привязанную группу обсуждений и автоматически закрепляет его там — см.
официальный анонс
[Discussion Groups](https://telegram.org/blog/privacy-discussions-web-bots)
и [API-документацию](https://core.telegram.org/api/discussion). Отдельного
выключателя автозакрепления в Bot API нет; доступен только
[`unpinAllChatMessages`](https://core.telegram.org/bots/api), который очищает
список закреплённых сообщений.

**Решение владельца (14.11):** группу оставляем подключённой, закрепов не
должно быть вообще. Поэтому:
- `pipeline.unpin_linked_discussion()` вызывается после каждого НОВОГО поста
  канала: проект, AI Brief, воскресный дайджест, воскресный опрос и замена
  опроса. Редактирование уже вышедшего сообщения новый автозакреп не создаёт,
  поэтому там вызова нет.
- `doctor --unpin-discussion` (флаг `unpin_discussion` в `doctor.yml`) один раз
  проверяет `linked_chat_id`, статус бота и право `can_pin_messages`, снимает
  уже висящие закрепы и повторным чтением чата убеждается, что список пуст.
- `unpinAllChatMessages` снимает **все** закрепы группы, включая возможные
  ручные. Это ровно соответствует запросу «хочу, чтобы закрепов не было».

Ошибка снятия закрепа логируется, но никогда не ломает публикацию: если бот
потеряет право `can_pin_messages`, пост всё равно выйдет, а закреп останется до
восстановления права. Это bounded best-effort без 100 % SLA.

**Не менялось:** связь канал↔группа, состав админов, расписание, число постов,
начало суток 03:00 Минск, живой Worker, Make/Sheet/webhook, секреты и
переменные репозитория, опросы как формат, уже вышедшие посты, state вручную,
PAT-ротация. Ручных публикаций и публикующих dispatch не было.
