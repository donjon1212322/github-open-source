# Правила владельца

Каждое правило здесь — прямое указание владельца канала. Часть из них
родилась из отвергнутых вариантов: если что-то здесь помечено «отвергнуто»,
не предлагайте это снова.

---

## Формат публикаций

### Длинный текст, не фото
Пост идёт **текстовым сообщением** (лимит Bot API 4096 символов), а карточка
прикрепляется **сверху как большой превью-блок** через `link_preview`.
Фото-пост отвергнут: подпись к фото ограничена 1024 символами, и история
не помещается.

### Карточки
- Горизонтальные **1200×630**. Квадрат и портрет — отвергнуты внутри канала.
- Стиль **Editorial Daily** по умолчанию, **Neon Terminal** для CLI/TUI,
  **Glass Aurora** только для AI Brief, **Editorial Sunday** для дайджеста.
- «Обводка не нужна» — рамку вокруг карточки убрать.

### Копирайт
- **Не сухой.** Никаких пресс-релизов и канцелярита.
- **Не заканчивается на «...»**.
- **Заголовки не для разработчиков.** Обычный человек, листающий ленту,
  должен захотеть открыть. Не `jargon`.
- **Технические названия моделей сохраняются полностью**: вендор + точное
  имя продукта + версия. `GPT-6.2`, а не «новая модель OpenAI».
- **Заголовки и подводки разделяются по площадкам:**
  - Telegram и статья — любопытный неспециалист;
  - Bluesky — проще и короче;
  - Facebook — самый простой язык.

### Картинки
- **Всегда на ImgBB.** Владелец требует явно.
- Порядок выбора: картинка из README репозитория → наша карточка →
  GitHub OpenGraph.
- Картинка из README тоже **перезаливается на ImgBB**, чтобы пост не
  зависел от чужого хостинга.

## AI Brief (новостной формат)

- **Отдельный формат, отдельный слот.** Ежедневно 19:10 по Москве
  (16:10 UTC), после последнего поста проектов.
- **Может выйти без первоисточника.** Для запуска модели или продукта само
  видео является свидетельством запуска.
- **Но без пометки «подтверждения нет».** Владелец отверг эту формулировку.
- **Сплетни и «левые» видео — не выходят.** Обзоры и запуски — да.

| Правило | Обоснование |
|---|---|
| **Ключи не трогать до продакшна** | «пусть лежат на своих местах до запуска проекта в продакшене» |

## Про запуск и целевую блокировку

**Правила приняты владельцем 2026-11-03.** Публикация разрешена, включение
`Doctor` и `Publishing pipeline` допускается. Порядок запуска и чек-лист
приёмки — в [`RUNBOOK.md`](RUNBOOK.md).

Ограничения, которые сохраняются всегда:

- **Target lock не отключать**: `main` доступен только при одновременных
  `APP_ENV=production`, `PUBLISH_TARGET=main` и заданном
  `TELEGRAM_MAIN_CHANNEL_ID`. Пустой тестовый ID никогда не подставляется вместо
  основного канала.
- **Тестовый канал 1:1 как продакшн**: без заглушек и тестовых пометок.
- Значения ключей остаются в GitHub Secrets/Variables, никогда не в git и
  никогда не в логах.
- Переключение на боевой аккаунт/канал и остановка прежнего бота — отдельные
  решения владельца.

> **Неофициальный проект.** «GitHub Open Source» — название канала и
> аккаунтов, проект не связан с GitHub, Inc. и не имеет прав на бренд
> GitHub. При переезде на боевые аккаунты добавьте пометку
> «Unofficial · not affiliated with GitHub, Inc.» во все описания.

## Решения владельца 11.11.2026 (после жалобы на опоздания в часы)

- **Внешний будильник — основной.** Worker `* * * * *` запускает команды
  через `workflow_dispatch` в нужную минуту; это проверено по логам Actions
  (start lag = 0). Запоздалый родной `schedule` GitHub **игнорируется**:
  если cron пришёл позже своего окна на 15 минут, команда НЕ выполняется,
  в state пишется `late_schedule_ignored`, владельцу уходит одно сообщение
  в сутки. Исключение осталось одно: `53 18 * * 4` (close+learn) — обе
  команды идемпотентны по ISO-неделе. 12.11 владелец велел починить и
  Facebook, поэтому `23 18 * * *` из исключений убран (см. ниже).
- **Почему это было важно.** 09.11 вечерние слоты отработали вовремя
  (`3578`, `3579`), а те же cron пришли повторно в 00:44 / 02:11 / 02:26 уже
  10.11 и опубликовали `3580`, `3581` и вторую статью. Они заняли дневной лимит публикаций
  и маркер «один бриф в UTC-сутки» следующего дня, поэтому
  вечерние слоты 10.11 честно вернули `slot_already_done` /
  `news_already_published`. Опоздание было не у поста, а у **дубликата
  будильника**, который съедал завтрашний день.
- **Бриф без свежих новостей не выходит, но молча не пропадает.**
  `duplicate_digest` / `not_a_digest` / `source_unavailable` /
  `gemini_ineligible` пишут маркер завершённого слота и одно личное
  сообщение владельцу; Watchdog больше не делает серию слепых ретраев.
- **0 corporate / IPO / S-1 / policy в брифе.** В промптах теперь прямо
  «ZERO such items», а статус `official_document` отсекается
  детерминированно. Конкретный инструмент/интеграция остаётся новостью.
- **Структура второй статьи:** как минимум два `###` H3 обязательны.
  Нормализатор больше не превращает `###` в `##` (в `5008047` было 11 H2 и
  0 H3 именно поэтому); если Gemini всё же не дал H3, два per-story H2
  понижаются до H3 структурно, без нового текста.
- **Явный rollback.** `FEATURE_TELEGRAM_DISCOVERY=true` заведена в repo
  Variables и продублирована в `.env.example`; `false` возвращает старый
  YouTube-путь без правки кода. Пустая переменная = default `True`.
- **Facebook:** `FEATURE_SHEETS_HANDOFF=true` **разрешён владельцем**
  («фейсбук включен, он работает нормально»). Запись «facebook-handoff не
  включать» отменена; Make/Sheet и webhook не менялись. 12.11 владелец
  отдельно велел починить и запуск: см. следующий раздел.

## Решения владельца 12.11.2026 («да сделай нужные правки включая фейсбук»)

- **Facebook остаётся ВКЛЮЧЁННЫМ**, но больше не зависит от пунктуальности
  родного GitHub cron. 11.11 `23 18 * * *` пришёл на 6,5 ч позже. Теперь у
  `facebook-handoff` есть ежедневный маркер в `last_runs` (идемпотентность
  по UTC-суткам), он добавлен в `watchdog.SLOTS` и запускается сторожем не
  позже 18:30Z; запоздалый `schedule` отклоняется общим guard. Make/Sheet,
  webhook, схема строк, секреты и флаг не менялись.
- **Снимок просмотров больше не теряется.** 11.11 due-диспатч `metrics` в
  20:23Z получил `startup_failure` — runner не выделился, маркера не было,
  догона не случилось. `metrics` теперь пишет маркер только после реального
  измерения и добавлен в `watchdog.SLOTS` (20:30Z): до трёх попыток, без
  слепой серии.
- **Статистика дедупа считает и вышедшие брифы.** Раньше счётчик
  писался только при пропущенном брифе, поэтому после `3587` с одним
  удалённым повтором отчёт всё ещё говорил «фильтр ни разу не сработал».
  Теперь строка появляется для каждого не-refresh запуска, а точные повторы
  не удваиваются.
- **Что НЕ менялось:** лимит публикаций, UTC-сутки, граница 03:00 Минск,
  cron-строки, живой Worker на момент фикса (позже в тот же день передеплоен
  под слоты США, см. раздел ниже),
  секреты, опросы и `MIN_SIGNAL_VOTES`, live-посты, state вручную.
  Гарантии 100 % по минутам по-прежнему нет: bounded best-effort, без SLA.

## Решение владельца 12.11.2026: посты для аудитории США

**Запрос:** «мне нужно что бы посты выходили для аудитории США», оба
побережья, ограничения менять разрешено, DST — на усмотрение агента.

- **Новые три слота (фиксированные UTC-минуты):** `01:13Z` (вечер ET /
  поздний день PT), `16:23Z` (утро PT / позднее утро ET), `18:13Z` (середина
  дня обоих побережий). Сбор кандидатов перенесён на `00:23Z`. Остальной
  «хвост» (статья, бриф, вторая статья, Facebook, метрики, кросспосты,
  модерация, недельный цикл) оставлен на своих минутах: он и так попадает в
  американский день.
- **DST выбран простой вариант:** фиксированные UTC. Зимой это 20:13 EST /
  17:13 PST, 11:23 EST / 08:23 PST, 13:13 EST / 10:13 PST; летом те же
  минуты дают 21:13 EDT / 18:13 PDT, 12:23 EDT / 09:23 PDT, 14:13 EDT /
  11:13 PDT. Оба побережья сдвигаются вместе и остаются внутри нужных окон,
  поэтому два набора cron не нужны.
- **Разрешение сдвинуть границу суток и число постов НЕ использовано.** Все
  три слота укладываются в одни и те же UTC-сутки (`01:13`, `16:23`, `18:13`),
  поэтому `03:00 Минск`, суточные маркеры и лимит в три публикации остались
  нетронутыми — так меньше риска сломать квоты и «один бриф в день».
- **Живой Worker передеплоен 12.11 в 03:54Z.** Due-слоты совпадают с
  cron `pipeline.yml`; старые минуты и имена `europe_*`/`us_peak` удалены.
  Секрет Worker `GH_PAT` заменён на PAT, присланный владельцем; секреты и
  переменные самого репозитория GitHub не менялись. `cli.main()` на всякий
  случай принимает только `us_evening` / `us_morning` / `us_midday` /
  `manual`: запоздалый или ошибочный dispatch становится `unknown_slot`
  без публикации. `watchdog.SLOTS` и родные cron остаются страховкой.
- **Не менялось:** Make/Sheet/webhook, `FEATURE_*`, секреты репозитория,
  UTC-сутки, граница 03:00 Минск, опросы, `MIN_SIGNAL_VOTES`, live-посты,
  state вручную. 100 % по минутам по-прежнему нет: bounded best-effort.

## Решение владельца 15.11.2026: одна метрика, честные реакции, без новых постов

**Запрос:** «сделаешь это?» — три пункта из таблицы в
`/home/user/VIEWS_AND_CADENCE_REASONING.md`. Владелец выбрал пункты 1 и 2;
по пункту 3 ответил «как будет лучше для вовлеченности и просмотров, если ты
посчитаешь что лучше пункт 3 пока не трогать, то не трогай его», а на вопрос
о слабом сигнале — «ничего не показывать, пока голосов меньше 8».

- **Зафиксирована одна метрика успеха:** **просмотры за сутки на пост**
  (медиана `views_at_24h`) плюс **сумма за день** (медиана дневных сумм
  `views_at_24h`). Оба числа уже есть в state; считает
  `insights.daily_view_metric()`, сравнивает последние 7 системных суток с
  предыдущими 7. Изменение внутри ±5 % честно называется «без изменений»:
  при ~20 постах в неделю это шум.
- **Сырые просмотры не метрика.** Пост вчера и пост трёхнедельной давности
  несравнимы: видимое «падение вдвое» было ошибкой возраста, а не работой
  бота. Нормализация по возрасту обязательна.
- Метрика показывается **только в личном воскресном отчёте владельца**,
  одной понятной строкой с вердиктом «выше / ниже / без изменений / смешано /
  мало истории». Публичные посты, число постов, слоты, cron, Worker, секреты
  и переменные не менялись. AI Brief в сумму не входит: его просмотры в state
  не пишутся — это честно отмечено в коде.
- **Реакции в снимке больше не нули.** Публичный виджет оборачивает эмодзи в
  `<i><b>…</b></i>` и ставит счётчик после него; старый шаблон считал только
  голый текст и записывал 0 для всех 35 замеренных постов. Теперь
  `fetch_post_stats()` читает реальные 1–2 сердечка, а `metrics_command`
  кладёт их и в `reactions`, и в `views_history`. Это влияет только на
  приватную оценку `value_score`; уже вышедшие посты и тексты не меняются.
- **Пункт 3 «показывать в канале, что изменилось после голосования» НЕ
  сделан, осознанно.** Причины: (1) при 5–7 голосах и пороге 8 выбранное
  владельцем правило «ничего не показывать» означает, что строка не появилась
  бы вообще — нулевой эффект на вовлечённость; (2) это противоречит правилу
  08.11 «результаты опросов только владельцу», защищённому отдельным тестом;
  (3) отдельный пост добавил бы лишнее сообщение в неделю, а по замерам
  более плотные дни дают меньше просмотров на пост. Решение обратимое: когда
  явка дойдёт до 8 или владелец изменит правило, строку можно добавить без
  смены каденции.
- **Что НЕ менялось:** лимит публикаций, граница 03:00 Минск, cron-строки,
  живой Worker, `MIN_SIGNAL_VOTES = 8`, формат дайджеста и опросов,
  публикующие dispatch, live-посты, state вручную, Make/Sheet/webhook,
  секреты и переменные репозитория. Ручных публикаций не было.

## 23.11.2026 — что не должно повторяться и какой должна быть выборка

- **Фальшивые «установщики» отклоняются.** В живой очереди стояли четыре
  репозитория от четырёх разных владельцев — PhpStorm, CLion, Microsoft Visio,
  iMobie AnyTrans, — с настоящей MIT-лицензией, ровно 336 звёздами у каждого и
  тегами вида `jetbrains-phpstorm-install-setup-2026`,
  `clion-download-windows`, `bentley-microstation-install-setup-windows-2026`,
  `anytrans-download-iphone-manager`. Это воронки за скачиванием чужого
  коммерческого продукта, а не open-source. Гейт отвечает
  `lookalike_installer:<topic>`; правило узкое (install/download + платформа
  или год), поэтому `setup`, `installer`, `download-manager` по-прежнему
  проходят. Защищено `tests/test_diversity_and_lookalike_2026_11_23.py`.
- **Разнообразие считается за неделю, а не за день.** Замер 16–23.11: 17 из 22
  постов — DevTools, 15 из 22 — про ИИ-агентов, Rust — 46 % языков. Причина в
  коде: бонус разнообразия сравнивал кандидата только с *сегодняшними*
  постами, поэтому первый слот каждого дня выбирал «голый» топ очереди.
  Теперь в селектор передаётся окно 7 дней и штрафуются: повтор языка (≥3),
  «затопленная» тема (≥5 постов одной семьи), совпадение ≥2 тегов и **повтор
  владельца** (−12). Это штрафы, а не квоты: тонкая очередь всё равно
  публикуется, а проект, который заметно лучше, по-прежнему выигрывает.
- **Токен источника не меняет язык канала.** `t.me/GitHubRadar` — русскоязычный
  канал; из него читаются только ссылки `github.com/...`, текст постов в канал
  не попадает.
- **Что НЕ менялось:** каденция и слоты, cron-строки, формат карточек
  (включая баннеры из README — владелец 23.11 решил оставить как есть),
  `MIN_SIGNAL_VOTES`, правила опросов, state вручную, секреты и переменные.

## 23.11.2026 (вечер) — «по звёздам судить не стоит»

- **Абсолютная популярность больше не решает.** Прямое указание владельца:
  судить по звёздам не стоит; молодой быстрорастущий проект — сильный сигнал.
  В модели 12 сигналов, сумма 100. Импульс (рост + ускорение + форки/сутки +
  «взлёт» новичка) весит **50**, популярность (`log10` звёзд) — **5**. Ровно
  10:1, поэтому трёхлетний проект с 20 000 звёзд и плоским ростом не может
  обойти новичка, который ускоряется.

  ноль: молодой репозиторий нельзя наказывать за то, что мы его только что
  увидели.

  владельца 23.11.** Механизм объяснён до кода, ветка запушена в `main`
  только после явного «пускай в продакшен».

## 23.11.2026 (ночь) — карточка победителя опроса

- **Формат выбран владельцем: вариант 10, «Tabloid».** Газетная первая
  полоса: кремовая бумага, чёрные чернила, красный акцент, три колонки
  THE VOTE / THE PICK / THE PROMISE, штамп `PROMISE KEPT` под −7°.
  Реализация — `src/ghos_v6/cards_poll.py`, 1200×630, тот же шрифт, что у
  остальных карточек канала.
- **Карточка только для Telegram и только для поста, который исполняет
  обещание.** Остальные платформы (dev.to, Hashnode, Bluesky) и статья в
  Telegraph получают штатную карточку: в `pipeline.py` карточка победителя
  присваивается **только** `preview_url`, `image_url` не трогается. Тест
  `test_the_card_never_leaks_into_cross_posts_or_the_article` следит за этим,
  мутация «карточка на постах без обещания» убивается.
- **Штатная карточка не меняется.** `cards.py` не тронут; если рендер или
  загрузка карточки победителя падает, пост выходит со штатной карточкой —
  обещание важнее картинки. Оба отказа пишутся в `events.jsonl`
  (`poll_card_failed`, `poll_card_unhosted`).
- **Нет голосов — нет карточки.** Газета заявляет результат только когда
  результат есть: если у обещания не подсчитано ни одного голоса (такое
  возможно только при сломанном подсчёте — `build_obligation` не открывает
  обещание с нулём), пост выходит со штатной карточкой, а в `events.jsonl`
  пишется `poll_card_skipped`. Тот же принцип внутри рендерера: недостижимый
  фолбэк говорит «The poll closed before a single vote was counted», а не
  «the readers chose» — уверенная ложь крупным шрифтом недопустима.
- **В тексте поста нет строки про опрос.** Владелец 23.11: пост, который
  исполняет обещание, ничем в тексте не отличается от обычного — никаких
  «вы это выбрали в опросе», никаких отсылок к голосованию. Единственная
  примета — карточка. Проверяется тестом
  `test_the_promise_post_text_carries_no_poll_line`.
- **Английский — единственный язык карточки.** Вопрос, имя проекта, описание
  и подписи — по-английски; русский остаётся в общении и в пояснениях.
- **Нестандартный вход не должен ломать карточку.** Текст проходит через
  `clean_text` (NFKC, контрольные и нулевые символы), `readable` (символы,
  которые шрифт не рисует, выбрасываются — CJK, арабский, цветные эмодзи),
  `wrap_lines` (перенос по словам, сверхдлинный токен — по `-/_.:`),

## 24.11.2026 — зазоры в три часа и воскресенье без проектного поста

Владелец на вопрос «важно ли американское окно, не разумнее ли разложить
посты ровно и разгрузить воскресенье» выбрал полный вариант. Основание —
измерение, а не вкус: нормализованные просмотры на 24-м часу по 61 посту
ноября дали 73 (01:13Z), 65 (16:23Z) и 64,5 (18:13Z) — вечерний слот ET
сильнее примерно на 12 %, а три поста подряд в 16:23/18:13/19:18 отбирали
друг у друга внимание. Воскресенье отдельно: дайджест с опросом выходил в
16:13, а проектный пост — в 16:25, то есть опрос жил **12 минут** в тишине
и собрал два голоса с 51 просмотра.

- **Новое расписание (UTC).** `01:13` — пост (20:13 ET / 17:13 PT);
  `15:13` — пост (10:13 ET / 07:13 PT, было 16:23); `18:13` — средний слот;
  `21:48` — AI Brief (было 19:18); `22:23` — вторая статья dev.to (было
  19:53). Зазоры между видимыми в Telegram постами: 3 ч 00, 3 ч 00 и 3 ч 35
  вместо 1 ч 50 и 1 ч 05.
- **Вечерний якорь не тронут.** Самый сильный слот (`01:13Z`, вечер ET)
  остаётся на месте: одного якоря достаточно, остальное подстраивается под
  него.
- **Воскресенье: слот `18:13` отдаётся дайджесту и опросу.** Проектного
  поста в этот день нет — объём недели не растёт, пост не «теряется», а
  уступает место опросу с тремя часами тишины вокруг. Реализовано в двух
  местах: `cli` выбирает команду по дню недели (один cron, не два — иначе
  они пересекутся в 18:13), `pipeline.publish_slot` пишет
  `sunday_digest_slot` и закрывает слот, чтобы сторож не гонялся за ним.
- **Опрос пока остаётся в воскресном дайджесте.** Через две недели решение
  по голосам: если за опрос 2–5 голосов — меняем местами среду (AI Brief ↔
  опрос) и **не** добавляем пост. Перенос опроса на другой день отложен до
  этих данных.
- **Просмотры меряются, а не extrapолируются.** `views_at_24h` — проекция:
  пост 23.11 на 22 реальных просмотрах «на 24 часа» показывал 84. Теперь
  при возрасте 24–36 ч пишется `views_measured_24h` и
  `views_measured_24h_age`, и именно эти числа отвечают на вопросы про
  расписание. Снимок не перезаписывается: одно измерение — один возраст.
- **Второй замер в 02:23Z.** Одного чтения в 20:23Z не хватало: посты
  01:13 / 15:13 / 18:13 при следующем чтении оказывались в возрасте 43 ч,
  35 ч и 26 ч — то есть вечерний якорь (самый сильный слот) не измерялся
  никогда, а 21:48 и 22:23 попадали в выборку 22-часовыми. Теперь просмотры
  читаются дважды в сутки, и у каждого поста есть ровно один снимок в окне
  24–36 ч. Ночной проход пишет собственный маркер `metrics-night`, чтобы
  сторож по-прежнему отвечал за вечерний слот 20:23.
- **Опоздавший слот не оплачивается соседним.** 24.11 слот 15:13 после трёх
  503 ушёл в 17:06 — за 67 минут до слота 18:13, а чуть более долгий простой
  дал бы пару с интервалом 13 минут. Прежний бюджет восстановления (4 часа
  при метке о простое, до 8 попыток) оказался длиннее нового зазора в 3 часа.
  Теперь сторож перестаёт восстанавливать проектный слот через
  `LATE_POST_LIMIT_MINUTES = 60` после его времени: день заканчивается на один
  пост короче, зато ритм сохраняется, а кандидат не пропадает — он остаётся в
  очереди для следующего слота. Худший возможный зазор — 2 часа.
