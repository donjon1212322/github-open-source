# Обещание по опросу: как оно устроено

Ветка `poll-obligation`. **Не в проде, не запушено.** Владелец 23.11: сначала
объяснить механизм, потом код; без подтверждения — не пушить.

## Проблема, которую это лечит

Опрос 19.11 закрылся ничьей 3:3, победителем записали «Blazing-fast native
notes app and rich-text editor for macOS, Windows, and Linux». Прошло десять
постов — ни одного проекта этого рода. Причины в коде были две:

1. Результат опроса писал только мягкие множители в `audience_profile`.
   Никакой даты, никакой проверки, никакой ответственности — забыть было
   нечем.
2. У победившего варианта был **пустой список GitHub-тем** (у того кандидата
   тем не было вообще), поэтому даже мягкий множитель равнялся ровно 1.0.
   То есть система не «слабо намекнула», а не сделала ничего.

## Что теперь происходит по шагам

| Когда | Что | Где |
|---|---|---|
| четверг, `poll-close` | закрытие опроса + `build_obligation()` | `pipeline.close_poll_command` |
| тогда же | в state появляется `poll_obligation` со сроком **+7 дней** | `state.json` |
| каждый `collect` | к обычной ротации добавляется поиск по терминам обещания | `sources.build_search_queries(obligation_terms=…)` |
| каждый `publish`, выбор | при открытом обещании сначала берётся подходящий кандидат | `rank.select_candidate(..., obligation)` |
| каждый `publish`, успех | публикация проверяется на соответствие → `fulfilled` | `pipeline._fulfil_obligation` |
| просрочка | `expired` + событие, в отчёте честная строка «не выполнено» | `pipeline._live_obligation` |
| воскресенье, `report` | строка «Poll promise: open / kept / not kept» | `pipeline.report_command` |

Три состояния, и все три видимы: `open` (есть срок), `fulfilled` (есть репозиторий
и дата), `expired` (есть событие). Промежуточного «ну как бы учли» нет.

## Откуда берётся пул

Пул не новый, он расширяется только на время обещания — и только тремя
запросами:

1. `topic:<термин> stars:>=50 archived:false fork:false`
2. `<термин> in:name,description stars:>=100 archived:false fork:false`
3. и то же для второго и третьего термина (всего максимум 3 термина → 6
   запросов).

Термины — это **темы варианта плюс слова из его текста**. Именно из-за текста:
в 19.11 темы были пустые, и без слов из формулировки обещание снова стало бы
пустым. Из текста отбрасываются слова, которые есть у половины GitHub
(`app`, `tool`, `fast`, `native`, `open`, `source`, …), и остаются
содержательные: `notes`, `editor`, `macos`, `linux`.

Обычная ротация (`sources.py::build_search_queries`) не меняется: три запроса
по дате создания, три по языкам дня, topic firehose по трём темам дня,
evergreen-lane. Замер 23.11: discovered 451 → enriched 120 → прошли гейт 52 →
в очереди 28. Обещание добавляет к этому несколько десятков кандидатов
конкретно по теме.

## Как это влияет на выбор

- При открытом обещании среди кандидатов, прошедших гейт и разнообразие,
  ищутся подходящие по теме; берётся лучший из них, даже если в целом по
  очереди есть кандидат с оценкой выше.
- Но не любой ценой: подходящий кандидат должен набрать хотя бы 20 баллов
  (`rank.OBLIGATION_MIN_SCORE`). Очередь и так состоит из прошедших гейт,
  так что порог отсекает только совсем мёртвое.
- Штрафы недельного разнообразия продолжают работать: обещание не может
  залить неделю одной темой, оно выбирает **какой** подходящий пост выйдет.
- Опрос «Show more X tools» (`reality_check`) обещает **тему**, а не проект,
  и считается выполненным первым же постом этой семьи. Опросы формата и
  глубины (`format`) не обещают ничего — обещания не создают.
- Ничья (`tied: true`) записывается как ничья, но формулировка всё равно
  становится целью: молчать после «3:3» хуже, чем выбрать.

## Система опросов меняется или нет

Сами опросы — нет: те же вопросы, та же каденция, тот же `MIN_SIGNAL_VOTES`,
тот же таймаут. Меняется **последствие**: раньше закрытие опроса влияло на
множители, теперь оно дополнительно создаёт датированное обязательство и
строку в отчёте. Ничего не удаляется — `audience_profile` и `learn`
продолжают работать как раньше.

## Что видит владелец, если обещание не выполнено

В воскресном отчёте:

```
Poll promise: not kept — no project matching "Blazing-fast native notes app…"
was published before the deadline
```

Это не извинение, а факт: система честно скажет, что не нашла. После
`expired` следующее обещание создаётся только следующим закрытым опросом —
долг не копится и не блокирует публикации.

- `tests/test_poll_obligation_2026_11_23.py` — 18 тестов: термины из текста,
  пустой список тем больше не обнуляет обещание (ровно случай 19.11), срок

  мутаций `132` (в том числе 6 новых — на обязательство).

## Карточка победителя (вариант владельца №10, «Tabloid»)

Пост, который закрывает обещание, выходит в Telegram с газетной первой
полосой вместо штатной карточки: `THE OPEN SOURCE DAILY`, номер выпуска,
заголовок из имени победившего проекта, три колонки THE VOTE / THE PICK /
THE PROMISE и штамп `PROMISE KEPT`. Колонки собираются только из известных
фактов — если даты нет, фразы о дате нет вообще; если голосов ноль, вместо
«0 of 0 readers» стоит честная фраза о том, что канал спросил, а читатели
выбрали.

Границы: карточка идёт **только** в Telegram-пост исполнения обещания
(`preview_url`), `image_url` для dev.to/Hashnode/Bluesky/Telegraph остаётся
штатной карточкой. Ошибка рендера или загрузки — фолбэк на штатную карточку
плюс событие в `events.jsonl`.

Ноль подсчитанных голосов — тоже фолбэк: обещание с пустым счётом не может
возникнуть честно (`build_obligation` возвращает пусто при `best <= 0`),
поэтому это признак сломанного подсчёта, и канал публикует пост со штатной
карточкой (`poll_card_skipped`), а не первую полосу с фразой «читатели
выбрали».

Проверено: `tests/test_poll_winner_card_2026_11_23.py` (40 тестов: 21 злой
вход, рамка 6 px, детерминизм, fuzz 40 строк, бюджет 3 с) и
`tests/test_poll_obligation_2026_11_23.py` (25 тестов, включая «карточка не
утекает в кросс-посты» и «сломанная карточка не блокирует пост»).
